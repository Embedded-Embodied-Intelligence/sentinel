# Sentinel — AI-driven project management

Sentinel is a research prototype of a goal-driven agent that manages a project under
uncertainty. It watches a project simulated on PSPLIB instances read as software projects
(activities, a team of four IT roles, absences, work increases and new activities), forecasts
the risk to explicit goals — the deadline, the budget and the stability of the plan — by Monte
Carlo rollouts, and chooses an intervention (re-timing, re-sequencing with CP-SAT,
substitutions, overtime) by simulating every candidate on the same sampled futures before it
acts; actions above its autonomy level go through a permission gate to a human. A language
model has three narrow roles only: turning team messages into events, proposing candidate
actions in a fixed grammar and explaining decisions, always through a record/replay cache and
never inside the simulation. The repository holds the formal model, the code, every committed
result and the generated tables and figures of the article and the course report.

> Status: release 1.0.0 (course project at Rzeszów University of Technology, 2026). The article
> (English, LNCS) and the course report (Polish) are added to the release package.

## Architecture

```text
   team messages, project descriptions           explanations
                 |                                          ^
+----------------v------------------------------------------+-----------+
| Interpretation (LLM, record/replay cache, JSON schemas)      spec §10 |
|   parse events · propose actions in a grammar · explain decisions     |
+----------------+-----------------------+------------------^-----------+
                 | validated events      | compiled         | decision
                 |                       | candidates       | records
+----------------v-----------------------v------------------+-----------+
| Decision (Sentinel)                                        spec §4–§6 |
|   observation -> needs gate -> candidates -> racing on shared worlds  |
|   -> lexicographic rule -> permission gate (auto / defer / escalate)  |
+----------------+------------------------------------------------------+
                 | rollouts, plans
+----------------v------------------------------------------------------+
| Computation (deterministic, seeded)                    spec §1–§3, §5 |
|   simulator · SGS heuristics · CP-SAT · Monte Carlo forecasts         |
+-----------------------------------------------------------------------+
```

The LLM proposes and interprets; the solver checks constraints; the rule chooses. Nothing an
LLM writes enters the decision layer except validated, compiled objects, and no rollout calls
an LLM. Packages and interfaces: [`docs/spec/architecture.md`](docs/spec/architecture.md).

## Quick start

Requires [uv](https://docs.astral.sh/uv/); it installs Python 3.12 if missing.

```bash
uv sync                                               # environment from uv.lock
uv run pre-commit install                             # git hooks (ruff, detect-secrets, hygiene)
uv run python scripts/fetch_psplib.py --sets j30 j60  # PSPLIB into data/psplib (not committed)
uv run pytest -q                                      # tests; data tests skip without data/
uv run pytest -q -m "data or slow"                    # data tests and slow tests (> 30 s; data > 3 s)
uv run sentinel inspect j30/j301_1                    # instance summary, LB0, reference makespans
```

Quality gate before every commit:
`uv run ruff check . && uv run ruff format --check . && uv run mypy src && uv run pytest -q`.

Benchmark data come from PSPLIB (Kolisch & Sprecher 1997) and are downloaded, never
redistributed; `data/psplib/MANIFEST.json` records source URLs and SHA-256 checksums.

## Project cockpit

`sentinel dashboard` simulates one project of the studies under two policies on the same world
(common random numbers) and writes one self-contained HTML file — no server, no network — with
the key figures side by side, the Gantt chart of baseline plan and realised execution, the
agent's risk forecast at every deliberation, and the decision log with the triggering events,
the chosen action, the runner-up, the deciding component, the permission gate and an
explanation:

```bash
uv run sentinel dashboard --set j30 --instance j3026_7 --replication 1 --lang pl \
  --out cockpit.html          # Sentinel against NoReaction on a WP5 world, Polish labels
```

Options: `--lambda-a`, `--delta-d`, `--policy` (any WP4 baseline or WP5 Sentinel variant,
default `sentinel_full`), `--compare` (default `no_reaction`), `--explain template|ollama|openrouter`
(LLM explanations through the cache, with their faithfulness check). The worlds of the studies
are reproduced exactly; [`docs/dashboard/`](docs/dashboard/README.md) holds three examples
chosen by a deterministic query over the WP5 results (`scripts/example_cockpits.py`).

## Application

`uv run sentinel ui` serves the application on <http://127.0.0.1:8000> (spec §11): *live projects*
that a project manager updates at check-ins, where Sentinel's recommendations below the autonomy
level apply automatically and the others wait for approval, and *simulator projects* on PSPLIB
worlds next to NoReaction. WP9a provides the JSON API (`/api/…`, its OpenAPI schema at
`/api/openapi.json`); the pages follow in WP9b. Projects, settings (the optional LLM provider and
its key, never returned by the API) and caches live in `--data-dir` (default
`$XDG_DATA_HOME/sentinel`, outside the repository). `uv run sentinel ui --demo` runs the public
demo: an anonymous sandbox per visitor with a showcase project and the limits of
[`configs/app_demo.toml`](configs/app_demo.toml).

## Reproducing the results

Every number, table and figure of the article (English) and the course report (Polish) comes
from code: `configs/paper.toml` lists the 14 committed result runs in `results/` with the
SHA-256 of their manifests and raw outputs, and `sentinel paper` turns their summaries into
`paper/generated/` (LaTeX macros `numbers.tex`, tables `tab_rq1.tex` … `tab_rq5.tex`,
figures `fig_rq*.pdf`; Polish versions in `paper/generated/pl/`) and rewrites the section
"Results at a glance" above. It refuses a run that is missing, a smoke run, recorded with
uncommitted changes, or whose files differ from the pinned hashes.

```bash
uv sync
uv run python scripts/fetch_psplib.py --sets j30 j60  # the RQ1 texts are narrated from PSPLIB
uv run sentinel reproduce --check                     # about 40 s, nothing recomputed
uv run sentinel paper                                 # writes paper/generated/ again
```

`reproduce --check` regenerates every summary of the 14 runs from their committed data files
and `paper/generated/` in a temporary directory, and compares every file byte for byte with
the committed one (117 files); exit status 0 means identical. It calls no LLM: the RQ1 error
analysis replays its sessions from the run's committed bundle.

**Full recomputation.** `uv run sentinel reproduce --commands` prints the prerequisites
(PSPLIB data, the `cpsat_det` baseline plans, the RQ5 decision states) and, per run, the
command recorded in its manifest with its recorded duration: about 23 h in total on the
4-core machine of `docs/infra/environment.md`, the longest 9.2 h (RQ4 main study), so run
them in `tmux`. A recomputed run gets a new directory under `results/`; configs that join
earlier runs read the committed ones.

**LLM runs without keys.** Each LLM run (RQ1, RQ5) commits its replay bundle
`llm_cache.jsonl.gz`; `--cache-file` answers every backend from it, without API keys,
Ollama or network, for example:

```bash
uv run python -m sentinel.experiments.wbs_study --config configs/wp6_rq1.toml \
  --out results/wp6 --cache-file results/wp6/20261023-215350-f5aad526/llm_cache.jsonl.gz
```

`--commands` prints this replay for each LLM run. The cloud answers came from
`openai/gpt-oss-120b` served by Groq through OpenRouter (provider pinned); a live rerun
would not return the same text, which is why the bundles are the reference.

## Release package

`uv run sentinel release --version 1.0.0` writes `dist/sentinel-1.0.0.zip` from `git archive`
of HEAD (tracked files only) with a generated `RELEASE.md`, refusing a dirty tree, and adds
files given with `--include` (the final PDFs) under `docs/deliverables/`. It never tags or
publishes; it prints the tag command.
