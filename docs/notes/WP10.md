# WP10 notes — the design system and an exploratory QA through the browser

**Purpose.** The owner judged the WP9 pages "functional but an engineering prototype". WP10 rebuilds
every screen to `docs/design/brief.md` (calm chrome, one accent, one number per screen, decisions
in a focus mode) on the same stack (ADR-0025, ADR-0027) and then drives the application as a manager
would, fixing what that finds. Research semantics are untouched: `reproduce --check` passes.

**The design system as implemented.** Custom-property tokens with the brief's values for light and
dark mode, mobile first (min-width queries at 480, 768, 1024). Components are Jinja macros
(`_ui.html`: badge, callout, delta line, chip value, date echo, field error) and partials (sidebar,
toast, Gantt, timeline, comparison). Icons are about 25 inline SVG line icons drawn for the project
(`ui/icons.py`), always `aria-hidden`, so a status always has a word. `focus.html` is the shell
without the sidebar for the wizard and a decision. A test holds the contrast of the tokens (4.5:1
text, 3:1 interface) and fails on a style nothing uses or a class no style defines.

**The Gantt.** An HTML column of focusable names beside an SVG whose x positions are percentages and
whose rows have a fixed height: it fills its card, its names stay in view when a phone scrolls the
plot, and rows take the focus, which rows inside `role="img"` may not (axe: nested-interactive).
Flags (status, today, deadline, the forecast window) are placed by a small greedy tier assignment,
tested to never overlap at the plot's least width.

**Forecast wording.** Every chance on the pages is the NoReaction forecast of §11.4. The simulator
makes that visible: a run read 0 % for weeks and then finished on time, because Sentinel kept
reacting. The pages now say "if the plan stays as it is".

**The manager's report.** The pages used to link the WP8 cockpit, a research artefact (model days,
task numbers, ISO dates, P(C ≤ D), decimals). `report.html` and `sim_report.html` are one
self-contained page each, from the same views, under the same wording check; the cockpit stays at the
API and `sentinel dashboard`.

**QA method.** `scripts/qa_run.py` starts `sentinel ui` on a fresh data directory and acts only
through the page (Playwright, Chromium); it reads the project's JSON in the same browser session for
its own books. A simulated team moves day by day: a task starts when its planned start has come, its
predecessors are done and its people are free; a partly present crew works at its share; real
lengths come from a seeded generator. Inputs: `docs/qa/zadania-portal.csv` (30 tasks),
`docs/qa/zespol-portal.txt` (11 people). Logs: `docs/qa/run1-log.json`, `run2-log.json`,
`wrong-log.json`. Evidence: `docs/qa/shots/`.

**A methodological note.** The first version of the driver's team stopped a task as soon as anyone in
its crew was away, while the engine lets the others work at their share. That alone turned a calm
project into a 3 % one, and the forecast was right about the wrong world. A QA driver of a forecasting
tool has to model the world as carefully as the tool does, or its findings about plausibility mean
little. Its second lesson: reading a chance as a verdict is the main risk of misreading; a chance
moves with what is reported, and the same project read 79 %, 46 % and 87 % within two weeks.

**References.** WCAG 2.2 (W3C 2023); axe-core 4.14 (Deque) for the automated scan; Nielsen 1994 on
severity ratings for the problem log; Nielsen and Landauer 1993 for the size of the usability test.
