# WP10 notes — the design system and an exploratory QA through the browser

**Purpose.** WP10 rebuilds every screen to `docs/design/brief.md` on the same stack (ADR-0025, ADR-0027),
then drives the application as a manager would and fixes what that finds. Semantics are untouched.

**The design system as implemented.** Custom-property tokens with the brief's values for light and
dark mode, mobile first (min-width queries at 480, 768, 1024). Components are Jinja macros and
partials; about 25 inline SVG line icons, always `aria-hidden`, so a status always has a word.
`focus.html` is the shell without the sidebar for the wizard and a decision. A test holds the tokens'
contrast (4.5:1 text, 3:1 interface) and fails on a style nothing uses or a class no style defines.

**The Gantt.** An HTML column of focusable names beside an SVG with percentage x positions: names stay
in view when a phone scrolls the plot, and rows take the focus, which rows inside `role="img"` may not
(axe: nested-interactive). Flags are placed by a greedy tier assignment, tested never to overlap.

**Forecast wording.** Every chance is the NoReaction forecast of §11.4: a simulator run read 0 % for
weeks and finished on time, as Sentinel kept reacting. The pages say "if the plan stays as it is".

**Threats (v2.1.1).** Ranked by late share minus on-time share, from 10 points. On run 1 this names
tasks at 1 of 9 check-ins; the largest difference elsewhere is 7 points. The same tasks hold the critical
chain in late and on-time futures, so lateness most likely comes from their lengths. Which task is on the
chain says little about a project with one dominant chain.

**The manager's report.** The pages used to link the WP8 cockpit, a research artefact. `report.html` and
`sim_report.html` are self-contained pages under the same wording check; the cockpit stays at the API.

**QA method.** `scripts/qa_run.py` starts `sentinel ui` on a fresh data directory and acts only
through the page (Playwright, Chromium); it reads the project's JSON in the same browser session for
its own books. A simulated team moves day by day: a task starts when its planned start has come, its
predecessors are done and its people are free; a partly present crew works at its share; real lengths
come from a seeded generator. Inputs: `docs/qa/zadania-portal.csv` (30 tasks), `docs/qa/zespol-portal.txt`
(11 people). Evidence: `docs/qa/shots/`, three JSON logs, `docs/qa/problems.md`.

**A methodological note.** The first version of the driver's team stopped a task as soon as anyone in
its crew was away, while the engine lets the others work at their share. That alone turned a calm
project into a 3 % one: the forecast was right about the wrong world. A QA driver of a forecasting
tool has to model the world as carefully as the tool does. Its second lesson: reading a chance as a
verdict is the main risk of misreading; the same project read 79 %, 46 % and 87 % within two weeks.

**References.** WCAG 2.2 (W3C 2023); axe-core 4.14; Nielsen 1994; Nielsen and Landauer 1993.
