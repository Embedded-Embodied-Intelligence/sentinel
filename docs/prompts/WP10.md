# WP10 — Redesign from the design brief; exploratory QA with two full project runs

Fresh session (`/clear`). Two tasks in order: **A** the redesign, **B** a hands-on QA session
whose report the owner reads on a phone.

<context>
- `CLAUDE.md`, `docs/spec/model.md` §11 (wording table), `docs/design/brief.md` (**the design brief,
  binding for task A**), `docs/notes/WP9b.md` (screen map, UX rules), ADR-0025 (front-end stack),
  `docs/ui/`, `docs/user-guide-pl.md`, `docs/usability/protocol-pl.md`
- skills `adr`, `spec-guard`, `wp-report`

The owner judged the current UI "functional but an engineering prototype". A senior-designer brief
(`docs/design/brief.md`, derived from top fintech and project tools without copying any brand)
defines principles, tokens, components and every screen's layout. The stack stays as in
ADR-0025 (server-rendered templates, HTMX, one hand-written CSS, no frameworks, no CDN, system
fonts). Behaviour, numbers and wording rules stay as in §11; this WP changes how things look and
are arranged, and fixes what QA finds.
</context>

<task>
**A. Redesign**
1. Implement the brief's tokens as CSS custom properties (light and dark), and its components as
   template partials (app shell, page header, hero metric, KPI tiles, status badge,
   recommendation card, comparison table, form fields, stepper, buttons, toasts, empty states,
   timeline, Gantt styling). Delete styles that are no longer used.
2. Rebuild every screen to the brief's layouts (start, wizard, overview, check-in, recommendation,
   history, project settings, simulator, app settings, how it works, error page), PL and EN.
3. **Visual self-review loop**: after each screen, capture it with the screenshot script at
   1280×800 and 390×844 (phone), compare against the brief point by point (hierarchy, spacing,
   one primary action, contrast), fix, and repeat until it matches. Keep the final pairs in
   `docs/ui/` (PL and EN; total ≤ 5 MB) and a short before/after note per screen in the report.
4. Keep every existing test green (internal-term checker, translations, accessibility scan with
   no serious violations in light and dark, e2e flows); add tests for the new components where
   they carry logic. ADR for the design system.

**B. Exploratory QA (after A)**
5. Run the app locally (`sentinel ui`, fresh data dir) and drive it **only through the browser**
   with Playwright, like a manager would, saving a screenshot at every step:
   - **Run 1, live project (6 working weeks):** create a 25–35-task IT project with the wizard
     (team by bulk paste, tasks by CSV), then do a check-in every 3–5 working days for six weeks
     of project time with realistic events (two absences, one task growing, one new task, normal
     progress), act on every recommendation (approve some, reject one, decide later once), use
     undo once, export the plan and the report, and check that history shows everything.
   - **Run 2, simulator:** the small and the medium example, Sentinel vs "nobody reacts", advance
     1, 5, 10 days and to the end; read the comparison and the report.
   - Also try what users do wrong: empty fields, cycles in dependencies, a deadline before the
     start, a CSV with errors, double-clicking buttons, browser back during a running job, two
     tabs on the same project, switching language mid-flow, a phone-size window.
6. Log every problem with severity (blocker / major / minor / cosmetic), steps to reproduce,
   expected vs actual, and a screenshot. **Fix** all blockers and majors (each with a regression
   test, in separate commits `WP10 fix: …`); list minors and cosmetics with a proposed fix.
7. Analyse the outcomes of both runs as a project manager would: did the forecasts move sensibly
   after events, were the recommendations understandable and plausible, did approving them help,
   did the simulator comparison tell a clear story, where would a manager hesitate or get lost.
8. **QA report for the owner, in Polish, readable on a phone**: `docs/qa/raport-qa-pl.md`
   (short paragraphs, headings, bullet lists, screenshots at phone-friendly width, no wide tables;
   ≤ 15 screenshots embedded, the rest linked): summary in 5 sentences; what was tested; results
   of run 1 and run 2 with the key moments; problems found and fixed; problems left with
   proposals; UX observations; recommendation for the usability test with people.

9. `wp-report` (`docs/reports/WP10.md`), roadmap row `WP10: done`, version 1.2.0, rebuild the
   release zip (do not tag).
</task>

<constraints>
- No change to research semantics; `reproduce --check` passes. No new runtime dependencies; no
  external fonts, icons from CDNs, or brand assets (inline SVG icons drawn for this project or an
  MIT/ISC-licensed icon set vendored with its licence are allowed).
- Default `pytest -q` ≤ 90 s; `e2e` separately. Commit after each screen group and each fix.
- Never wait for a process with `pgrep -f <name>` in a shell loop (CLAUDE.md).
</constraints>

<acceptance_criteria>
1. Every screen rebuilt to the brief, PL and EN, desktop and phone screenshots committed.
2. Quality gate, `-m "data or slow"`, `-m e2e`, accessibility scan and `reproduce --check` pass.
3. QA runs 1 and 2 completed through the browser; all blockers and majors fixed with tests.
4. `docs/qa/raport-qa-pl.md` complete; report, roadmap, 1.2.0 zip; pushed; clean tree.
</acceptance_criteria>

<report_format>
`docs/reports/WP10.md` via `wp-report` (English); the owner's reading copy is
`docs/qa/raport-qa-pl.md` (Polish).
</report_format>
