# WP12 — Fixes from the CEO/QA exploratory test: one set of numbers, calendar, check-in, AI, corrections

Fresh session (`/clear`). Last feature WP before the usability test with people.

<context>

  binding: every item B1–B24 and every UX friction is answered**), `docs/design/brief.md`,
  `docs/reports/WP10.md`, `docs/reports/WP11.md`, ADR-0025, ADR-0028
- skills `spec-guard`, `adr`, `wp-report`

An agent playing a CEO and QA lead tested the public demo at 1.3.0 for an hour. Verdict: the
overview and the recommendation card are the best "one screen for the board" in this class, but
**trust in the numbers is 2/5** (dates differ between screens, a promise differs from the result
after approval, holidays are ignored, big jumps have no explanation) and **status reports are 2/5**
(a text-only report silently means zero progress, the AI silently drops half a message). This WP
fixes that, in the priority order below. The research core is not touched: every change is in the
application layer or its spec section §11.
</context>

<task>
Work in this order; commit after each group (`WP12: …`, fixes `WP12 fix: …`), each with tests.

**A. One set of numbers (B2, B3, B4 and the frictions about jumps and recommendations)**
1. **Promise = result.** Approving a recommendation with nothing else changed must show on the
   overview exactly the chance, finish dates and budget the card promised (same worlds, same plan,
   same seed as the comparison). Find why B3 differs (39 % → 55 % promised, 46 % shown; budget +2 %
   promised, +6 % shown; 1 % → 5 % promised, 14 % shown) and fix it; add a regression test that
   asserts equality. If something legitimately changes the number after approval, the overview
   says what in one sentence.
2. **One date function.** Every date on every screen (overview, card, history, Gantt, CSV, HTML
   report) comes from one function from day index to date; the off-by-one cases of B4 disappear.
   The deterministic plan date and the forecast dates are labelled differently everywhere ("plan
   bez zakłóceń" vs "najbardziej prawdopodobny koniec"), and the Gantt explains the gap between the
   plan's end and the forecast window in one line.
3. **The plan shown is the current plan.** Gantt, CSV and the HTML report show the residual plan
   at the last check-in: no unfinished task in the past, all dependencies respected including new
   tasks (B2: "RODO" must end before "Testy"), checked by `validate_schedule` in the export path
   and in a test. The original baseline dates stay available as a separate column.
4. **Why did the chance move?** After each check-in, decompose a change of ≥ 5 points into its
   causes by one-at-a-time counterfactuals on the same 200 worlds: for each event of that
   check-in (each absence, growth, new task, the progress reported, the passage of time without
   progress), the chance without it. Show at most 3 lines on the overview ("Bez nieobecności
   Tomasza szansa byłaby 41 %"), computed in the background job like the threat list, with a
   sentence that the effects do not add up exactly. Spec §11 via `spec-guard`.
5. **Recommendation cards say what improves.** When the chance does not change (B: "0 % → 0 %"),
   the impact chip shows the deciding component (expected delay, overtime, plan changes) in words.
   When no recommendation is made at a low chance, the overview says how many options were checked
   and that none helps enough, with a link to the comparison. Options worse than "no change" are
   labelled so in the comparison; options with identical truncated names are distinguishable.

**B. Calendar (B5)**
6. Polish public holidays as non-working days in the application calendar (computed, no new
   dependency: fixed dates including 24 December since 2025, Easter Monday and Corpus Christi
   from the Easter date), plus a project setting for extra company days off (dates list). The
   day index in the application counts working days of this calendar; LiveContext and every date
   on screen use it. The simulator and research instances keep abstract days. Spec §11 via
   `spec-guard`; tests for 2026–2027 holidays and for a project spanning Christmas.

**C. Status reports (B9–B16 and the frictions)**
7. A report that moves the date forward without any progress on running tasks asks before saving
   ("Czy od <data> nic się nie posunęło?" with "Tak, brak postępu" and "Uzupełnij postęp").
8. A report date in the future is confirmed once per report, not after every failed save; the
   change counter is correct after any reload (B12); Enter in the role field adds the role (B11);
   Back during a save does not lose the report silently (B10: warn on leaving with unsaved changes).
9. Progress is stored in whole days: show what was saved ("60 % → zapisano 67 %, 2 z 3 dni")
   (B13). "Zakończone dnia" defaults to the report date (B16).
10. Growth of a task that has not started (B6, B15) is accepted as an estimate revision if the
    live model can represent it; decide with `spec-guard` and either support it or show why not.
    The task pickers list only the tasks each section accepts, grouped and labelled.
11. B14: make the deferral message match the actual rule (or the rule match the message), with a
    test that a deferred proposal reappears when the message says it will.

**D. AI features (B6, B7, B8)**
12. **Nothing is dropped silently.** The status-message flow shows, next to the items to confirm,
    the parts of the message it did not turn into an item, and asks when a name is not in the team
    (pick a person or ignore) or a task is ambiguous (pick from the candidates, e.g. two testing
    tasks). The JSON schema gains an `unparsed` list; the review page renders it. Research parser
    (§10, RQ1 prompt and corpus) unchanged.
13. **Explanations in the interface language**, plain words, none of the internal terms (run the
    existing internal-term checker on the AI text; on a hit, regenerate once, then fall back to the
    template explanation). Prompts stay in English; record in an ADR that user-facing model output
    may be in the UI language while prompts and research data stay English (CLAUDE.md invariant 3
    clarified in one sentence).
14. **Describe the project in words:** "około tygodnia" = 5 working days (the calendar facts go
    into the context), optional tasks recognised ("możemy z nich zrezygnować") and an "Opcjonalne"
    column in the preview, short task names (≤ 6 words, the sentence kept as the description),
    "testuje całość" depends on all earlier development tasks. Check with both providers on the
    CEO's text and on the WP11 texts; record the results.
15. Docker: the Ollama address placeholder shows the container address when running in Docker.

**E. Corrections after tracking has started (top-10 #8)**
16. Tasks that have not started can still be corrected after the first check-in: estimate, crew,
    dependencies, optional flag; each correction is a history entry and triggers a new forecast.
    Started and finished tasks stay locked, and the lock is a calm information box, not "Coś poszło
    nie tak". Spec §11 via `spec-guard`. If the live model cannot do this safely within the WP,
    stop at the information box and record the reason and a design in the report.
