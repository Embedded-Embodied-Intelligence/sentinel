# WP14 — Status messages that understand a whole report, with dates resolved by code; voice input

The owner's rehearsal of the usability test (1.4.1, demo, gpt-oss-120b, report dated Wed 4 Nov 2026)
typed task 3 as a message:

> „Warsztat z klientem" skończył się wczoraj, we wtorek 3 listopada.
> „Baza danych i API" trwa, zrobiono około 15 %.
> Bartosz Kowalski od jutra jest nieobecny i wraca w poniedziałek 16 listopada.

The review showed **one** item, and it was wrong: "Bartosz Kowalski: nieobecność od śr. 4 lis,
powrót śr. 18 lis" (expected: from Thu 5 Nov, back Mon 16 Nov; 11 Nov is a holiday). The other two
sentences landed under "Tego nie zamieniłem na zmianę" because the message flow only knows
absences, growth and new tasks. A manager's natural report is exactly these three sentences, so
the feature fails its main use. The likely cause of the dates: `LiveContext` asks the model for
working-day numbers shifted by an offset, so the model counts days, across a holiday, and gets it
wrong. The owner also asks for **voice input**: typing a report is tedious; speaking it is faster.
Typing stays.
</context>

<task>
1. **Dates are resolved by code, never counted by the model.** The application's message schema
   (not the research parser of §10, its prompt or the RQ1 corpus) asks for calendar dates
   (`YYYY-MM-DD`) and the phrase they came from; the context lists the report date with its
   weekday and the working days and holidays of the next 8 weeks. Code turns dates into day
   indices with the project calendar, checks that a named weekday matches its date ("poniedziałek
   16 listopada"), applies the "do / wraca w" reading of §11.3, and treats "od jutra" as the next
   working day after the report date. A mismatch or a non-working day becomes a question on the
   review, not a silent shift. The review shows absence dates as the first day absent and the
   return day ("nieobecny od czw. 5 lis, wraca pon. 16 lis").
2. **The whole report in one message.** The message flow also understands progress ("zrobiono
   około 15 %", "w połowie"), completion with a date ("skończył się wczoraj"), and a start
   ("ruszyło w poniedziałek"), mapped to the same fields as the check-in form and shown as items to
   confirm, prefilled into the form when confirmed. Task names match the project's tasks
   tolerantly (quotes, case, inflection); ambiguous matches ask. Spec §11 via `spec-guard`.
3. **An evaluation set for the app's messages**: `docs/qa/ai/messages-pl.jsonl`, 30 Polish
   reports on the usability project and the showcase project (the owner's message above
   verbatim; relative and absolute dates; dates across 11 Nov and Christmas; "do piątku" vs
   "wraca w piątek"; several facts per message; unknown names; ambiguous tasks; nothing to
   report), each with the expected items. A script scores items (exact match of type, task or
   person, and dates/values) per provider. Run it with gpt-oss-120b (budget below) and once with
   qwen2.5:7b on the first 10; report the scores before and after tasks 1–2. Target with
   gpt-oss-120b: ≥ 90 % of items exact and **no wrong date shown without a question**.
4. **Voice input** (an addition to typing, in the message box of the check-in and of "describe
   the project"): a microphone button records in the browser (MediaRecorder; no new runtime
   dependency, no external script), shows a timer and a stop button, uploads the audio to the
   server, which transcribes it with Groq's Whisper (`whisper-large-v3-turbo`, language `pl` or
   the UI language, with the team's names and the task names as the vocabulary prompt) and puts
   the text into the box for the user to read and correct before "Przetwórz wiadomość". Nothing
   is processed until the user presses that button.
   - Audio is never stored or logged; the transcript is not stored either unless the user saves
     the report (privacy mode as for messages); the request log records only that a
     transcription happened and its duration.
   - Limits: 90 s per recording, the demo's daily AI cap counts transcriptions, friendly errors
     (no microphone permission, no key, provider down), the button hidden when no Groq key is
     configured; works over HTTPS and on localhost.
   - The settings page tests transcription; the guides (PL, EN) and the deploy guide say that the
     audio goes to the cloud provider, as typed messages do with a cloud model.
   - ADR for the transcription design (cloud Whisper now; a local Whisper as a future option and
     why not now: CPU speed on this server, a new dependency).
   - Test it end to end with a generated Polish recording of the owner's message (e.g. text to
     speech, or the recording fixture you create; record how), and with Playwright's fake
     microphone for the UI.
5. Re-run the usability scenario's task 3 by message and by voice in demo mode; update the tester
   instruction notes in `docs/usability/README.md` (task 3 may be done by form, message or voice).
6. Version 1.5.0, rebuild the zip from a clean tree (do not tag), `wp-report`
   (`docs/reports/WP14.md`).
</task>
