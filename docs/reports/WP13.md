## Decisions

- **Request log behind a flag, on in the demo's config.** The WP asks for logging in demo mode
  only; a flag (`request_log`, ignored outside the demo) lets the owner switch it off after the
  test without a code change, so the demo collects no more than the test needs (ADR-0030).
- **Path template from the matched route** (`scope["route"].path`): no parsing, no ids, no
  query; an unmatched path is logged as an empty template.
- **Two fields beyond the four named.** The project, only if it is one of the sandbox's own (an
  id typed into a URL is dropped), tells the tester's project from the showcase and the
  simulation; the HTMX flag tells a page opened from the parts a page loads by itself (job
  polling, fragments), which the page-request count must leave out. Neither is personal data.
- **The log's write in a worker thread** (`run_in_threadpool`): an insert costs about 19 ms on
  this disk (the commit's sync), and the async request guard should not hold the event loop
  for it; the response still waits for the row, so nothing is lost on a restart.
- **Export read-only, no Store.** It opens `sentinel.db` with `mode=ro`, so the running demo is
  untouched and no migration runs on it; it never reads `secret.key`, cookies or addresses, and
  writes project labels instead of ids.
- **The overview's forecast after the plan is computed again** from the log: it is not stored,
  and it is deterministic for the project's state (spec §11.4), so the log shows the 69 % and
  Wed 2 Dec the tester saw at task 2. Chances and shares are rounded with the pages' `Texts`.
- **Task durations** each from the end of the task before (task 1 from the sandbox's first
  request); task 3 includes task 2, which leaves no trace (the card's clock times split them);
  task 4 ends at an approval or a rejection ("decide later" does not end it); task 5 at the
  first advance job that finished the simulation. Refused forms are POSTs answered 4xx/5xx (an
  error or a question to confirm); the setup's autosave always answers 200.
- **The scripted baseline now runs in demo mode** (the showcase, 60-day steps, two workers), as
  the remote testers see it, on a patched "today" 12 Nov 2026 (the pages read `date.today()`).
- ADRs created: ADR-0030.

## Commands for the owner

The public demo was left running (tmux `sentinel-demo`, started on 1.4.0). This WP changed no
template or static file, so it keeps working until it is restarted; after the restart its
database is at schema version 2, which an older Sentinel refuses to open.

```bash
# 1. Restart the public demo on 1.4.1 (migrates its database, starts the request log; ~5 s)
cd ~/projects/sentinel && git pull
scripts/run_demo.sh stop && scripts/run_demo.sh start
scripts/run_demo.sh check && scripts/run_demo.sh status    # `scripts/run_demo.sh funnel` if it is off
curl -s http://127.0.0.1:8000/api/health                     # "version":"1.4.1","demo":true

# 2. A dry run as P0 in a private window, then read docs/usability/logs/P0.md
uv run python scripts/usability_logs.py --data-dir ~/.local/share/sentinel-demo --code P0

# 3. After each tester, within 24 hours of their start (P2, P3 the same)
uv run python scripts/usability_logs.py --data-dir ~/.local/share/sentinel-demo --code P1
#    -> docs/usability/logs/P1.md

# 4. SUS of the answer cards, one "P1 4 2 4 1 5 2 4 2 4 1" per line
uv run python scripts/sus_score.py --file sus.txt

# 5. After the last tester: request_log = false in configs/app_demo.toml, then
scripts/run_demo.sh stop && scripts/run_demo.sh start

# Optional: tag the release
git tag -a v1.4.1 -m "Sentinel 1.4.1" 492a2a1c9eaf && git push origin v1.4.1
```
