## Summary
The three AI features of the application now work end to end through the browser with
`qwen2.5:7b` on Ollama and `openai/gpt-oss-120b` on Groq through OpenRouter: the settings
page's test of each provider, a project described as a list and as prose, a check-in message
with two facts, and the explanation with its faithfulness badge. The runs found 14 faults, fixed
in four `WP11 fix` commits with tests; no absence reason reached stored data, caches, logs or
pages, and model failures show a plain message while the form keeps working. The release zip
installs on a clean machine by following `RELEASE.md` literally (2 min 41 s from unzip to a
passed `reproduce --check`), after six gaps in its instructions were fixed. The Docker image is
not built yet: the server has Docker but not its compose and buildx plugins, so task 2 waits for
the owner's install. Version 1.3.0 is built as a zip, not tagged.

## Decisions
- ADR-0028: the application adapts only its own AI calls (limits, plain failures, a
  request-scoped cache, prompt aids, display-only wording); the study paths stay as they are.
- The prompt aids live in the app's parser context, not in the shared prompt file, so the
  committed replay bundles keep their request keys.
- A role the AI names that nobody in the team has stays in the crew and blocks the plan, rather
  than being dropped or mapped to a guess: the manager decides.
- The work of the earlier, interrupted WP11 session was reviewed (one word-boundary bug fixed:
  "OT" matched the start of "OTHER") and split into one commit per fault group.
- The live driver scores extraction against what each text states and sweeps every artefact for
  the absence reason; three local runs are kept because the small model varies between runs.
- The README leads with the application (what, a screenshot, three ways to run it, the guides);
  the research overview follows under "Research".

## Spec questions
1. **"Until <weekday>".** "Ania jest chora do piątku" ("ill until Friday"): spec §10.2 and the
   prompt read a weekday as the return day `r` (back on Friday); the natural Polish reading is
   absent through Friday (back on Monday). `gpt-oss-120b` gave Monday; `qwen2.5:7b` Friday once
   and Tuesday twice. Reading used: unchanged (the spec's), marked `SPEC-Q` in
   `app.llm.LiveContext.render`; the manager confirms each item before it is saved. Question:
   should "until <weekday>" give `r` = the working day after that weekday, and "back on
   <weekday>" `r` = that weekday?

## Open issues / next steps
- `qwen2.5:7b` is not reliable on these flows: the return day of the message was right by the
  spec in 1 of 3 runs, 3 of 6 explanations were faithful, and the prose lost a task in 2 of 3
  runs; the review catches it only if the manager reads it. For messages and explanations a
  cloud model is the better default; a review that lets the manager correct a date would help.
- Both models attribute Sentinel's recommendation to "the project manager" or "the agent"; the
  faithfulness check does not test who decided. A prompt of the app's own could say so.
- The spec question on "until <weekday>".
- The default `pytest -q` takes 86–89 s against its 90 s budget: the next tests must be tiny
  or `slow`.
- Task 2 (Docker) once the plugins are installed; then `docs/deploy.md`'s Docker section gets
  the measured size and start time, and the zip is rebuilt.
