The three AI features of the application now work end to end through the browser with
`qwen2.5:7b` on Ollama and `openai/gpt-oss-120b` on Groq through OpenRouter: the settings
page's test of each provider, a project described as a list and as prose, a check-in message

## Decisions
- ADR-0028: the application adapts only its own AI calls (limits, plain failures, a
  request-scoped cache, prompt aids, display-only wording); the study paths stay as they are.
- The prompt aids live in the app's parser context, not in the shared prompt file, so the
  committed replay bundles keep their request keys.
- A role the AI names that nobody in the team has stays in the crew and blocks the plan, rather
  than being dropped or mapped to a guess: the manager decides.
- The work of the earlier, interrupted WP11 session was reviewed (one word-boundary bug fixed:
  "OT" matched the start of "OTHER") and split into one commit per fault group.
- The live driver scores extraction against what each text states and sweeps every artefact for
  the absence reason; three local runs are kept because the small model varies between runs.
- The README leads with the application (what, a screenshot, three ways to run it, the guides);
  the research overview follows under "Research".
- Default provider: one provider per server, as before (the owner's choice over sending messages
  and explanations to the cloud while descriptions stay local). With Groq or OpenRouter the
  default model already was `gpt-oss-120b`, so the change is the recommendation where the
  provider is chosen, with the privacy advice beside it.
- The return days of "until" and "back on" are written out per weekday in the app's parser
  context, like the other WP11 aids, so the shared prompt and the replay bundles keep their
  request keys.
- The demo's AI settings were stored by `LlmService.update`, the settings page's own code, with
  the key loaded by `load_secret` and never printed, instead of starting a second server on the
  live demo's database (`deploy.md` step 3): the running demo is an older version.
- `scripts/docker_check.py` runs as its own compose project on port 8002, so a deployment's
  volume is never touched; `SENTINEL_PORT` rather than an override file, since a company server
  may have port 8000 taken, as this one does. It checks both a restart (the container stays) and
  `down` with `up -d` (only the volume stays).

## Spec questions
None open.
1. **"Until <weekday>"** (answered). "Ania jest chora do piątku" ("ill until Friday"): spec §10.2
   and the prompt read a weekday as the return day `r` (back on Friday); the natural Polish
   reading is absent through Friday (back on Monday). The answer, spec v2.1.5 (§11.3, the
   application only): "until <weekday>" ("do <weekday>") gives `r` = the working day after it,
   "back on <weekday>" ("wraca w <weekday>") `r` = that weekday; §10.2, its prompt and its corpus
   stay. Implemented in `LiveContext.render`; the `SPEC-Q` marker is removed.

## Open issues / next steps
- `qwen2.5:7b` is not reliable on these flows: its return days (Friday, Tuesday, Tuesday) are
  all wrong by v2.1.5 (Monday), 3 of 6 explanations were faithful, and the prose lost a task in
  2 of 3 runs; the review catches it only if the manager reads it. The settings page and guides
  now recommend the cloud model; a local run with the v2.1.5 context is not measured, and a
  review that lets the manager correct a date would help.
- Both models attribute Sentinel's recommendation to "the project manager" or "the agent"; the
  faithfulness check does not test who decided. A prompt of the app's own could say so.
- The default `pytest -q` takes 86–89 s against its 90 s budget: the next tests must be tiny
  or `slow`.
- In Docker the settings page's address field shows the placeholder `http://127.0.0.1:11434`,
  while an empty field uses `OLLAMA_HOST` (`http://ollama:11434`): it works, but the placeholder
  misleads; the field's hint could name the preset address.
- The demo's AI spends the owner's OpenRouter credit, capped at 200 calls a day.
